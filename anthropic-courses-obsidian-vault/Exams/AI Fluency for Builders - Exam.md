# AI Fluency for Builders — Study Group Exam

**Grounded in:** the official curriculum for [AI Fluency for Builders](https://anthropic.skilljar.com/ai-fluency-for-builders) (built by Anthropic with CodePath), plus the underlying [[4D Framework]] from Anthropic's foundational *AI Fluency: Framework & Foundations* course, which this one builds on and lightly re-covers.

**Honest note on method:** built from the official lesson outline plus verified framework definitions — not a transcript quiz. One specific gap: the course evaluates AI-generated code across "five lenses," but the exact names of those five lenses aren't public — see [[Discernment for Code (Five Lenses)]], left as a skeleton for you to fill in from the lesson video.

**Course shape, for reference:**
1. **Introduction and AI Fluency framework** — Welcome · The 4D Framework
2. **How AI works** — AI capabilities & limitations
3. **The 4D framework for builders** — [[Delegation]] & the builder's toolkit · [[Description]] & building great things · [[Discernment]] for builders ([[Discernment for Code (Five Lenses)|Discernment for code]] · Discernment for user experience)
4. **Tying it all together** — Stand behind what you build *(this is where [[Diligence]] lives)*
5. **Wrapping up** — Closure & looking forward · Course quiz

**The 4D Framework, in brief:** see [[4D Framework]] for the full hub note — [[Delegation]], [[Description]], [[Discernment]], [[Diligence]].

**How to run this with your group:** solve solo first, no peeking — budget 45–60 min. Sections A–F are objective; score 1 point each (47 pts total) and compare. Sections G and H are for the call — this is the framework you'll actually be selling to clients, so don't rush the discussion part.

## Section F — Sequencing (4 pts)

**Q45.** A builder gets a vague Slack message: *"Checkout feels slow, can you fix it?"* Put these four steps in the order the 4D Framework (plus the Description Chain) would suggest. Write 1–4 next to each:

___ Evaluate the AI's proposed fix — does it address the actual root cause, does it introduce risk, does it meet your engineering bar?
___ Decide this is a good candidate to hand to AI *with* human review — not a zero-oversight handoff
___ Turn the vague complaint into a precise, testable instruction (e.g., "checkout load time exceeds 3s on mobile; profile it and propose fixes; target under 1.5s")
___ Ship, monitor real usage, and be ready to fix or roll back

*(Note: in real work these steps loop and overlap constantly rather than running once in a straight line — this is a simplified teaching example, not a rigid checklist.)*

### Section G — discussion guide
46. Skipped **[[Discernment]]** (no real review) — arguably also **[[Diligence]]** (nobody's actually vouching for what shipped). Risk: a 3,000-line unreviewed change to a *billing* system is about as high-stakes as it gets — financial errors, compliance exposure, silent bugs.
47. The **[[Description Chain]]** should have turned "make onboarding better" into something concrete first: what's actually broken, for which users, measured how, bounded by what constraints — *before* any prompt got written.
48. Check discernment on the experience itself: does it match real user mental models, is it consistent with the rest of the product, does it actually reduce confusion — functional correctness is necessary but not sufficient. See [[Discernment]].
49. **Transparency Diligence.** Worth saying plainly to the stakeholder: undisclosed AI involvement in customer-facing financial conversations is a trust and, in a lot of jurisdictions, a compliance issue — "premium" isn't worth that exposure. See [[Diligence]].
50. They're proposing **[[Modes of AI Interaction#Agency|Agency]]**. Good questions before recommending it: what's the actual cost of a wrong autonomous decision at that dollar threshold, and what audit trail / human escalation path exists if something goes wrong?
51. This is a **[[Delegation]] triage** problem: not every task deserves the same model or the same review depth. Help them build simple tiers — e.g., low-risk/reversible tasks get a cheaper model and light review; high-risk/hard-to-reverse tasks get the capable model and real human review. Match effort to stakes, not habit.
52. **Deployment Diligence** — verifying and standing behind what actually goes out, even in a personal context. Real risk: a mismatched or generic application can actively hurt candidacy (wrong company name, wrong skills emphasized), and 200 unread submissions burn trust with recruiters fast. See [[Diligence]].
53. A strong structure: (1) what was delegated and why it seemed reasonable at the time, (2) how it was described/instructed, (3) what discernment step was skipped or done too quickly, (4) what diligence practice you'd add now (a review step, a disclosure, a verification habit) to prevent the repeat.

### Section H
54. Open discussion — a strong answer usually notes that "literacy" implies passively knowing *about* something, while "fluency" implies an active, practiced *skill* you get better at through use — which matters for builders because shipping product is a practice, not a comprehension test.
55. Open — the value is entirely in doing this out loud with your group on a real example, not in a written answer.
